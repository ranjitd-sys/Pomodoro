Today, our system relies on the existing Durable Streams server running from the provided Docker image. LiveStore communicates with that server through the Durable Streams protocol, and the server is responsible for stream creation, appends, reads, offsets, replay, SSE synchronization, and other stream lifecycle behavior. Internally, the reference implementation uses components such as server.ts, store/file-store abstractions, subscription management, and its own persistence mechanisms.

Our goal is not to modify LiveStore, the client-side sync implementation, or the Durable Streams client APIs. Instead, we want to build our own Effect v4 implementation of the Durable Streams server that behaves compatibly with the existing server from the client's perspective. The new implementation will use Effect EventJournal (specifically a SQL-backed EventJournal implementation) as the authoritative persistence layer and source of truth for stream events and ordering.

The objective is that LiveStore can switch from the existing Durable Streams server to our Effect-based server without any client-side changes. The server must provide the synchronization guarantees, offset management, replay behavior, SSE behavior, and protocol semantics required by LiveStore and validated by our existing architecture and synchronization test scenarios. We'll start with the specific protocol operations LiveStore currently uses (PUT create, POST append, GET catchup/long-poll) rather than the full reference server surface (subscriptions, webhooks, fork headers, producer epochs, compression, fault injection) — those advanced features exist in the reference implementation but are not in our current test scenarios, so they come later if needed. We are reproducing the required Durable Streams behavior using Effect and EventJournal, not redesigning the synchronization architecture or reimplementing LiveStore itself.
